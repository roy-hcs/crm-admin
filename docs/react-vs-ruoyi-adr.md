# ADR-001：SPA 拆分 vs RuoYi 服务端渲染（测试、权限与边界）

> 状态：已接受（2026-10-29）相关：测试策略见
> [react-test-plan.md](./react-test-plan.md) §16；功能缺口与 RBAC 缺口见
> [react-feature-drift-analysis.md](./react-feature-drift-analysis.md) §4。

## 1. 背景与事实

本仓是 RuoYi（Thymeleaf 服务端渲染）后台的 React 重写。做决策前先确认以下事实（2026-10-29 实测）：

| 事实             | 数据                                                                                                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 应用规模         | 146 条生效路由、158 个 `*Page.tsx`、约 244 处 `api*()` 调用点                                                                                         |
| 后端契约         | atlas `openapi.admin.json`：806 条 path（OpenAPI 3.0.3）                                                                                              |
| 后端权限         | 133 个 Java 文件使用 `@RequiresPermissions`，权限点体系在后端**完整存在**                                                                             |
| 后端脱敏         | 4 个文件使用 `@DataMask`                                                                                                                              |
| 认证方式         | session cookie（`credentials: 'include'`），非 token                                                                                                  |
| 前端权限         | **无权限点体系**：无 `GET /system/user/permissions` 之类接口（atlas 与 `SysLoginController`/`SysMenuController` 均无），菜单在 `Sidebar.tsx` 静态定义 |
| 前端按钮显隐     | 按业务状态（如出金单状态 1/4）判断，越权时由后端返回错误                                                                                              |
| 旧版页面数据来源 | 大量页面由 `ModelMap` 注入，没有 JSON 读取接口（详见 gap 清单 §二）                                                                                   |

## 2. 决策

1. **继续 SPA 拆分**，但把收益归因于**边界显式化**，而不是"换成 React"本身。
2. 拆分必须交付三样东西，否则只是把复杂度搬进浏览器：**显式契约（atlas + 契约测试）**、**前端可见性裁剪（最小 RBAC，见 §5）**、**可分层验证（见测试方案 §16）**。
3. 后端保持**唯一安全权威**：`@RequiresPermissions`
   不因前端裁剪而放宽；前端只做 UX 层裁剪。

## 3. 理由：两种方案的测试与工程对比

| 维度         | RuoYi + Thymeleaf                                            | SPA（本仓）                                            |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------ |
| 最划算的测试 | Spring `MockMvc`：参数绑定 + 权限注解 + view model，一次到位 | 纯函数单测（L1）+ 契约（L2）+ 组件提交体（L3）         |
| 最便宜的测试 | 无：逻辑与视图混在模板内联 JS、`ModelMap`，没有中间层        | 毫秒级单测，无需中间件                                 |
| 页面行为测试 | 只能整页浏览器 E2E，选择器依赖 `th:each` 生成的 DOM，脆且慢  | 组件级断言 + 少量纵切 E2E                              |
| 契约         | 隐式（controller ↔ 模板变量），无独立契约层                 | 显式 JSON 契约，可被 atlas 与契约测试锁定              |
| 反馈速度     | `@SpringBootTest` 常需数据库/Redis/RabbitMQ 等依赖           | 前端测试离线毫秒级，无中间件                           |
| 造数据       | 一条 SQL / 一个事务即可                                      | 需 fixture 或后端种子数据（E2E 更麻烦）                |
| 权限裁剪     | 服务端渲染天然"看不到就没有"                                 | 需前端 RBAC 权限点，否则整页下发（见 §5）              |
| 部署与发布   | 前后端同包，页面改动即后端发布                               | 前端可独立发布；代价是契约版本需对齐                   |
| 新增缺陷类别 | —                                                            | **契约不同步**（漂移清单中占比最高的一类）、可见性泄露 |

结论：拆分不是"更容易测"，而是**让分层测试成立**；同时它主动放弃了服务端自带的权限裁剪与廉价造数，这两笔代价必须显式偿还。

## 4. 后果

**正面**

- 计算/格式化/校验从模板里被挤到纯函数，可被毫秒级单测覆盖（这是本仓缺陷最集中的地方）。
- 契约成为一等公民：拼错 path/参数名能被 L2 直接捕获。
- 前后端可独立演进与发布；前端可离线开发（MSW + fixtures）。

**负面（需偿还）**

1. **契约不同步**：重构期靠与旧版差异比对，长期靠 atlas 契约测试。
2. **可见性泄露**：后端照常返回整页数据，前端未裁剪 → 无权用户能"看见但不能操作"，敏感字段依赖
   `@DataMask` 兜底。
3. **E2E 造数成本上升**：需要后端种子数据或 fixtures，阻塞了 Playwright 落地（见测试方案 §11）。
4. **atlas 维护责任**：契约快照过期会让 L2 失灵，需明确更新机制（测试方案 §15.3）。

## 5. RBAC 缺口与处理方案

### 5.1 现状

- 后端权限点完整（133 个文件、`@RequiresPermissions`），越权请求会被拒。
- 前端无权限点：菜单静态、按钮按状态显示、无路由守卫 → 表现是"能点、点了报错"，以及"不该看到的数据仍然下发到浏览器"。
- 目前 `permissionJson` 一类字段是
  **CRM 客户的权限包配置**，与后台管理员 RBAC 无关，不能复用。

### 5.2 原则

1. 安全边界**只在后端**；前端裁剪用于降低信息暴露面积与误操作，不作为防线。
2. 无权限默认**隐藏**而非置灰（置灰仍泄露"存在此操作"）。
3. 权限码**沿用旧版字符串**（如
   `system:crmWithdrawVerify:cancel`），不重新设计命名，避免双份权威。

### 5.3 方案对比

| 方案                    | 内容                                                                                                                                | 成本                            | 风险/缺点                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------- |
| A 维持现状              | 不裁剪                                                                                                                              | 0                               | 可见性泄露、误操作提示差                                 |
| **B 最小 RBAC（采纳）** | 后端新增 `GET /system/user/permissions`（返回权限码 + 角色）；前端 `usePermission` / `<Can>` / 路由守卫；菜单加 `perm` 字段后被过滤 | 后端 1~1.5 人日 + 前端 2~3 人日 | 需维护前端权限码与后端一致（可加一致性校验）             |
| C 菜单树下发            | 后端下发菜单树，前端动态注册路由                                                                                                    | 8~12 人日                       | 与现有静态路由重复，收益集中在"减少重复维护"，当前不划算 |

**采纳 B**。落地顺序：

1. 资金与审核（权限点集中且风险最高）：出金/入金审核、余额调整、代客入金、返佣审核；
2. 系统管理（角色、菜单、管理员）；
3. 菜单按权限码过滤（`Sidebar.tsx` 的 `MenuItem` 增加 `perm`）。

### 5.4 验收标准

- 任一权限组合下：无权时**不发请求**、不渲染入口；
- 直接构造请求越权时，后端返回 403/错误码（后端既有能力，需回归用例覆盖 1~2 条）；
- 权限变更走 RuoYi 已有的操作日志，前端不新增审计链路；
- 一致性：前端用到的权限码必须能在后端 `@RequiresPermissions`
  中检索到（可做成 L2 契约测试的一条用例）。

## 6. 被否决的替代方案

| 方案                                      | 否决原因                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------- |
| 回退到 Thymeleaf，放弃 SPA                | 放弃已投入的 146 条路由与可分层测试能力；模板内 JS 与 `ModelMap` 的耦合是当前多数缺口的根因 |
| 只在 RuoYi 内补测试（MockMvc + Selenium） | 覆盖不到"纯函数/组件提交体"这层最便宜也最有效的测试；Selenium 维护成本高                    |
| 前端自建权限点体系（重新定义码值）        | 与后端 133 个 `@RequiresPermissions` 形成双份权威，必然漂移                                 |

## 7. 与测试策略的关系

- L2 契约层在重构期做**与旧版的差异比对**，长期做**调用点存在性断言**（测试方案 §9、§16.4）——ADR 与测试方案共用同一套基础设施。
- 最小 RBAC 的"权限码一致性"可作为 L2 的一条用例，防止前端引入后端不存在的码。
- E2E 造数成本（§4 负面 3）决定 L4 只能做少量纵切，不能铺页面。

## 附录 A：待决策——只读数据接口由谁写

> 背景：B 类 23 个页面卡在"旧版由 `ModelMap`
> 注入、无 JSON 读取接口"，而后端排期满。是否允许前端（AI 辅助）补这类接口，尚未决定。以下为建议边界，待评审。

**允许做（纯序列化型）**

- `GET` 只读，且与旧页面 `ModelMap` 注入的数据**一一对应**；
- 复用既有 service 方法，**新增 `@ResponseBody` 方法**，不改 SQL、不加联表；
- 必须复制旧页面的 `@RequiresPermissions`；
- 列表必须分页，禁止全量返回。

**禁止做**

- 新增 SQL / 联表 / 聚合 / 导出 / 跨服务调用；
- 用"前端过滤"代替后端数据范围过滤（这就是越权读）；
- 涉及敏感字段但不做白名单或脱敏的返回体。

**必做配套**

- 后端 owner code review（写代码的人可以是前端）；
- 接口写回 atlas（重新生成 `openapi.admin.json`），否则 L2 契约测试看不到它；
- 在 [react-migration-gap-analysis.md](./react-migration-gap-analysis.md)
  与漂移清单标注"前端补接口"，明确责任归属与联调窗口。

**风险提示**：只读不等于低风险——越权读泄露、无分页打挂库、字段口径与旧页不一致形成"第二套真相"，这三类都会在只读接口上发生。
